# Part A — Open items in the protocol

## A1. Imperial units

- **Proposal:** keep imperial units out of the standard.
- **Discussion:** no counter-arguments were raised.
- **Decision:** agreed. Imperial units stay out of v1.0.

## A2. Queue management

- **Proposal:** keep queue management out of the standard for now (for example in v1.1).
- **Reasoning:** the current proposal is not mature enough. Including it now would be too ambitious.
- **Discussion:**
  - Q: Does that mean we keep using, for example, the existing queue management protocol?
  - Clarification: the **setup** part is part of the standard. Queue management can be solved in
    other ways and is not standardized.
- **Decision:** agreed.

## A3. Definition of the MQTT topics

Starting point, the previously agreed shape: `prefix/version/site/machine/message-type`

### Version in the topic?

- **Question:** do we want the version in the topic, or is the version in the JSON enough?
- **Arguments for leaving it out:**
  - The envelope already carries the version (not under discussion).
  - It keeps the protocol and the transport separate.
- **Counter-arguments:**
  - When an upgrade happens, the topic would not need an upgrade but this communication might be broken still (less enforcement).
  - Versions cannot run in parrallel.
- **Note:** in case of version added strongly advised to use the major/breaking version
- **Decision (by vote):** the version is **left out** of the topic.

### Direction in the topic?

- **Question:** do we need a direction segment (`send` / `receive`)?
- **Decision:** **yes**, direction is added to the topic.

### Follow-up

- Once the scheme is final, write down a sample topic for each message type.

## A5. Message property: movement status

**Ref:** [`docs/message-properties.md`](../docs/message-properties.md) § *Movement status*,
Technical Guide (logistics status, `movement` field)

- **Request:** delete the movement status, which is currently optional.
- **Discussion:**
  - What would the reason be for removing it?
  - If it is provided, it is "open book". What if someone else would deliver this information?
  - Some suppliers already offer this information. The standard is extensible either way, but by
    keeping it, those who provide it now do so in the same format.
  - Goal: make clear which data is standardized, and where.
- **Consequence of keeping it optional:** parties still have to negotiate whether it is provided.
- **Observation:** this was the first discussion about actual implementation and the business side.
- **Decision:** agreed to add an extra line stating this is "not in the standard". *The exact
  wording and placement still need to be agreed.*

### A5 clarification by maintainer — 14 October 2026

**Later confirmation, not part of the October 1 minutes:** on 2026-10-14 the maintainer answered
**“agreed”** to the following wording, placement and schema alignment:

> Providing movement status is optional and subject to agreement between supplier and customer.
> When provided, use the movement values defined here.

Place this line above the Movement status table in Message Properties and reference it from
the technical guide. This resolves the earlier “not in the standard” wording as no obligation
to supply movement information, while preserving its defined format when supplied. The original
minutes above remain historical; their wording/placement question is now settled.

The maintainer also explicitly approved making `movement` optional inside a supplied logistics-
status entry. Remove it from `LogisticsStatusItem.required` during coordinated alignment;
retain `statusId` as required and preserve the existing movement enum. The parent logistics
information remains optional. No new values, commands or movement-control behaviour are added.

The schema and normative documents implement this clarification. Final package approval
remains separate.

- The technical guidance is felt to be confusing. If we know exactly what is missing, we can always
  extend it.
- Proof point: an implementation was done by an AI agent based purely on this definition.
- The underlying problem seems to be that the **German text** does not quite meet expectations.

- Reuse the first sentence of the GitHub README.

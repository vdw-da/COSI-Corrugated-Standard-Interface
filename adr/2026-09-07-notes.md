# Decisions taken

## D-2609-01 · Guide is released as version 1.0 (finding #36)

The technical guide, and all companion documents, move to **version 1.0** now — not to a
release candidate. Cover page version, date and status are updated, and the revision history
gets its 1.0 row.

**Owner:** André Seifert. **Status:** decided, to be applied.

## D-2609-02 · `l2rSequenceNumber` is required on every corrugator order (finding #16)

Resolves the contradiction between the glossary ("on each order") and the schema (required
only in the non-production `else` branch).

**Decision:** in `setup-corrugator`, `l2rSequenceNumber` is required on **every non-empty order
object in the `orders` array**, production and non-production alike. The schema is corrected;
the glossary was already right.

**Status:** decided, to be applied. Schema change — carries this note as its decision trail.

## D-2609-03 · Paper grammage is named `gsm` (finding #43)

The same physical property carried two names: `weight` on the corrugator, `grammage` on
converting. Neither wins.

**Decision:** the field is named **`gsm`** on both machine types. Unit of measure is
**`g/m²`** in metric. The imperial counterpart is **not part of v1.0** and is parked as an
idea for a later version.

**Status:** decided, to be applied.

**Maintainer's note for the Oct 1 session — please confirm:** the capture sheet records the
imperial unit as `MSF`. `MSF` is *thousand square feet*, an **area** unit; imperial basis
weight is expressed as **`lb/MSF`** (pounds per thousand square feet). Recording `MSF` alone
as the unit of a grammage would be dimensionally wrong. Since imperial is parked, nothing is
blocked — but the parked idea should carry `lb/MSF`, not `MSF`. The later notation confirmation is recorded in ADR-000012.

**Second implication:** `gsm` is an abbreviation, and `docs/naming-conventions.md` § 3 admits
abbreviations only from an explicit permitted list. `gsm` must be added to that table when the
rename is applied.

## D-2609-04 · Metric only for v1.0; imperial booked as an idea for 1.x (finding #21a)

The 2026-07-15 tendency is confirmed as a rule. v1.0 is **metric only**, and this is written
explicitly into `docs/naming-conventions.md` rather than left implicit. Imperial support is
recorded as an idea for a 1.x release, not as a v1.0 gap.

**Status:** decided, to be applied.

## D-2609-06 · Bidirectional data flow is east-west only (guide Open Issue 03, finding #37)

**Decision:** bidirectional communication is permitted **only east-west** — hardware to
hardware, within the production level. It is **never** permitted north-south, i.e. between the
production level and the supervisory/cloud level, which stays unidirectional.

Open Issue 03 is thereby closed and the outcome is written into the guide as a rule.

**Status:** decided, applied 2026-09-08 — with one amendment, below.

### Amendment 2026-09-08 (maintainer) — the axis is IT/OT, and the missing word is *direct*

The minute above is self-contradictory as written. Read literally, "never north-south … between
the production level and the supervisory/cloud level" outlaws the standard's own setup write path
— § 4 setup delivery, ADR-000006 (response), ADR-000007 (retained queue) and ADR-000008 (delete request)
are all ERP/MES → machine flows. The maintainer established three corrections:

1. **The axis is IT/OT segmentation, not cloud.** ERP/MES are IT, machine controllers are OT.
   North-south is not forbidden; forbidden is north-south **direct**. The sanctioned crossing is
   the MQTT broker at Level 3.5 — which is why § 2.2 and § 4.2 already demand an MQTT adapter
   from any manufacturer offering REST. Brokered north-south is the normal, required path.
2. **The zone split is stated explicitly:** OT = Levels 0–3, IT = Levels 4–5. This follows
   mechanically from the existing name of Level 3.5 (*IT/OT Integration Layer*) but the guide
   never said it.
3. **The prohibition is symmetric** — both IT→OT and OT→IT direct. The minute, and the first
   correction, addressed IT→OT only.

East-west remains peer-to-peer inside one zone (controller ↔ controller in OT, ERP ↔ MES in IT);
that direct hardware-control path stays permitted and is out of scope of this standard.

Applied as: guide § 2.4 *Communication Directions* block, § 4.10 retitled *Issue Log* with Issue
03 marked **Closed**, four glossary rows (OT, IT, north-south, east-west), and
[ADR-000010](ADR-000010-bidirectional-east-west-only.md).

**Status:** applied 2026-09-08, **to be confirmed on 2026-10-01** — all three corrections publish
wider than the minute (later ratified on 2026-09-24; see ADR-000010).

## D-2609-07 · Cosmetic set (findings #17, #18, #34)

- **#17** — volume unit is written **`m³`** per ISO, replacing plain `m3` (performance water
  and air, and the preferred-units table).
- **#18** — `faultCode` is constrained to the pattern `^[A-Z]{3}$`, matching its own description
  and the closed table in `docs/corrugated-faults.md`.
- **#34** — the orphan throughput unit `kicks/h` is dropped from the glossary; **`pcs/h`** is
  used instead.

**Status:** decided, applied 2026-09-08 — with one amendment, below.

### Amendment 2026-09-08 (maintainer) — #18 is an `enum`, not a `pattern`

The minute above records `^[A-Z]{3}$`. On review the maintainer established that the code table in
`docs/corrugated-faults.md` is **fixed for v1.0** — 40 codes, no additions before a version change.
`docs/naming-conventions.md` § 10 requires a closed value set to be expressed as `"enum": [...]`,
and a pattern would accept any three capitals, e.g. `XYZ`. The field therefore carries the explicit
enum of the 40 codes plus `null`, generated from the table and round-trip verified against it.
Nothing is lost: `OTH` (not classifiable) and `UNK` (cause unclear) remain in the set, and
`internalCode` stays a free vendor string.

**On the ISO reference.** The citation was uneditioned. It now reads **ISO 14224:2016, Annex B**
across all four surfaces. Note for the group: in the ISO 14224 **first edition (1999)** the
foreword states that "Annexes A, B, C and D of this International Standard are for information
only" — the failure-mode notation is a recommended taxonomy, not a normative constraint. The 2016
edition was not available to verify (paid document), so the published wording claims only the
edition and annex, never normative status. The closedness of the VDW list is VDW's own decision.

**Status:** applied 2026-09-08, **to be confirmed on 2026-10-01** (same treatment as ADR-000009).

## P-2609-02 · Numeric precision is not prescribed (finding #21b)

Direction agreed: the standard does **not** prescribe decimal precision, and says so explicitly
instead of staying silent. Text is prepared ahead of the session; **working-group confirmation
required on Oct 1.**

### Amendment 2026-09-08 (maintainer) — the guide text ships ahead of confirmation

`docs/technical-guide.md` § 2.1 carried the only precision statement in the repository: "Use
consistent decimal separators and precision". Two faults. **Decimal separators are not a choice** —
JSON permits exactly one (`.`), per the specification linked in the bullet directly above it, so
that half was dead text. **"Use consistent … precision" reads as a soft prescription**, pointing the
opposite way to the direction agreed here. Rather than leave a published contradiction standing
until Oct 1, the maintainer replaced the bullet with the decided rule:

> — **Precision is not prescribed** — producers send the precision their source provides; consumers
> must not assume a fixed number of decimal places

This is the only precision surface in the repository (`grep -rn -i "precision|decimal"` over
`README.md`, `docs/`, `schemas/`, `examples/` returns this line alone), so no sweep followed.
The proposed naming-conventions text is **not** written — that surface stays
empty until the group confirms.

**Status:** guide text applied 2026-09-08, **to be confirmed on 2026-10-01** (numeric precision, same
treatment as ADR-000009 and the #18 enum).
